## CA-01 — Handle only on manual gates

### Verbatim (Italian)

```txt
Nessuna porta che sia di tipo animato deve averla la maniglia ma solate quelle manuali
```

### Reading

"No gate of the automated type should have the handle — only the manual ones." (`animato` = `automatizzato`, `solate` = `solo`.)

### Normalized rule — `CONFIRMED`

- `motorised === true` → **no handle** anywhere: not in the 2D schematic, not in the 3D mesh, not in the fabrication cut list / BOM.
- `motorised === false` → handle is present and should be visible in the preview.
- The handle is part of the base build, not a priced option. Removing it on automated gates does **not** reduce the `FROM` price.

### Rationale

An automated gate is operated by remote/keypad; a handle on the leaf is both useless and a snag hazard. This is a build rule, not a preference — treat it as a hard constraint, not a default the customer can override.

### Downstream impact

| Target | Change |
|---|---|
| `packages/gate-engine/src/rendering/render-plan.ts`, `packages/gate-engine/src/mesh/` | Handle is currently **not modelled at all**. When it is added, gate it on `!config.motorised`. |
| `packages/gate-engine/src/fabrication/cut-list.ts` | Exclude handle hardware when `motorised`. |
| `apps/web/src/lib/client-intake/questions.ts` | Add confirmed seed for a new `open.handle_rule` question so the client is not asked again. |

### Still open

- Handle position/side on a **single swing** leaf (relates to `gate.single_swing.default_handing`, still unanswered).
- Handle style/finish — is there one standard part, or a choice?
- Manual **sliding** gates (tracked / cantilever / telescopic): is the same handle used, or a different pull?

## CA-03 — Finish palette and colour charge

### Verbatim (Romanian — sent twice in the same batch, identical text)

```txt
Sostituiamo zinc grey/ bronze si pearl white cu satin black/gloss black/matt black/
anthracite 7016/ care sunt toate £55/m2 plus VAT. Si sa fie Una casella…optiune unde sa
Isi puna si culoarea dar aia o sa fie extra pret…nu stiu exact dar £250/300 cam Asa
ceva…oare putem lasa doar + extra charge powder coatings? Si apoi le specific eu pretul
final in email?
```

### Reading

> We replace zinc grey / bronze / pearl white with satin black / gloss black / matt black / anthracite 7016 — which are all £55/m² plus VAT. And there should be a box, an option where the customer can also enter their own colour, but that will be an extra price… I don't know exactly, maybe £250/300, something like that… could we just leave "+ extra charge powder coatings"? And then I specify the final price in the email?

### Normalized rule

**Palette — `CONFIRMED`.** The standard palette is exactly four finishes:

| Code | Label | Status |
|---|---|---|
| `black_satin` | Black satin | standard |
| `black_gloss` | Black gloss | standard |
| `black_matt` | Black matt | standard |
| `anthracite_ral7016` | Anthracite RAL 7016 | standard |
| `other_ral` | Other RAL colour (customer-entered) | quoted separately |

**Retired — do not reintroduce:** `zinc grey`, `bronze`, `pearl white`. These appear in older docs as the generic fallback four; they are now explicitly withdrawn by the client.

**Rate — `PARTIAL`.** £55/m² **plus VAT**, stated as applying to all four standard finishes.

**Custom colour — `CONFIRMED` as a policy decision.** The client asked whether we can show only "+ extra charge — powder coating" and settle the number by email. **Answer: yes, and that is the safer option.** So:

- `other_ral` shows **no number** in the configurator.
- It shows "Custom RAL — powder coating quoted separately" and flags the quote request.
- The £250–£300 figure is an **internal indication only**. It must never reach a public surface or a PDF quote.

### Why the rate is `PARTIAL`

Three parameters are missing and each one changes the total:

1. **Is a colour already inside the `FROM` price?** If black satin is included and the other three cost +£55/m², the configurator behaves completely differently than if every finish is +£55/m² on a bare galvanised base.
2. **What is the m²?** Gate face area (`width × height`)? Both faces? Actual painted surface?
3. **Does the rate really apply to Victorian?** Traditional Victorian is open bars — a fraction of the painted area of a solid composite panel of the same face dimensions. A flat £55/m² of *face area* would overcharge Victorian heavily.

Intake question `open.finish_uplift_rule` (blocking) already asks exactly this and remains open.

## CA-05 — Cantilever tail = 1/3 of the clear opening, minimum

### Verbatim (Romanian)

```txt
Cantilivered gates trebuie sa aiba coada porti 1/3 din deschiderea intre stalpi….
(ex 4000mm intre stalpi, coada 1333mm minimum deci 4000mm poarta + 1333 coada = 5333mm
minim totalul porti.
```

### Reading

> Cantilevered gates must have a gate tail of 1/3 of the opening between the posts. (e.g. 4000mm between posts → tail 1333mm minimum, so 4000mm gate + 1333 tail = 5333mm minimum total gate.)

### Normalized rule — `CONFIRMED`

```txt
clearOpeningMm      = distance between posts = the width the customer enters
tailMm              = clearOpeningMm / 3          (MINIMUM, rounded up)
totalAssemblyMm     = clearOpeningMm + tailMm     (≈ 1.333 × clearOpening)
```

Worked example from the client: `4000 → tail 1333 → total 5333`.

Two intake answers fall out of this:

- **`gate.cantilever.tail_ratio`** → `1/3 of the clear opening, minimum` — **answered**.
- **`gate.cantilever.width_meaning`** → `clear_only`. The configurator width is the opening between posts; the tail is additional and must be *shown* on top of it — **answered**.

### Site-space consequence, and why it belongs in the UI

A customer entering 4000mm must be told they need **5333mm of clear run** on the parking side, plus post and hardware clearance. This is the single most common cantilever site failure. Surface it as a live note on the dimensions step, not buried in a survey PDF.

### Code delta — the current constant is now wrong

`packages/gate-engine/src/rules/cantilever.ts` today:

```ts
export const CANTILEVER_TAIL_RATIO_AT_4M = 1 / 3
export const CANTILEVER_TAIL_RATIO_DEFAULT = 0.28   // ← now superseded by CA-05

export function getCantileverTailRatio(widthMm: number): number {
  return widthMm === CANTILEVER_RULE_WIDTH_MM
    ? CANTILEVER_TAIL_RATIO_AT_4M
    : CANTILEVER_TAIL_RATIO_DEFAULT
}
```

The `0.28` fallback and the `widthMm === 4000` special case both existed only because 4m was the one confirmed data point. CA-05 states the rule generally: **1/3 at every width**. Required change:

- single ratio constant `CANTILEVER_TAIL_RATIO = 1 / 3`, applied for all widths;
- keep it as a **minimum** — the client said "minimum", so a larger tail is valid, a smaller one is not;
- `cantileverTailNote()` should stop saying "shown schematically" and state the real rule plus the total run;
- delete `CANTILEVER_TAIL_RATIO_DEFAULT` and `CANTILEVER_RULE_WIDTH_MM` rather than leaving them unreferenced;
- the module docstring claiming "the only client-confirmed data point is a 4m opening" is now stale — cite CA-05.

Both consumers (2D render plan and 3D mesh plan) already read from this module, so the fix lands in one place.

### Still open

- Maximum cantilever width (`gate.cantilever.size_limits`).
- Foundation/base frame length as a function of the tail (`gate.cantilever.foundation`).
- Whether the tail is visible in the closed-state preview or only in the open state (`gate.cantilever.support_visibility`).
